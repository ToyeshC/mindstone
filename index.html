Teaching AI Who You Are

The hard part isn't the code. It's knowing what to say.

A shared opening frame

These widen "how to use AI" to "what it means to live with it".

For Everyone

The Four Layers

Most people use AI like a search engine. The ones getting real value have built a system around it. That system isn't code. It's clarity about who you are, what you need, and what you want it to do.

There are four layers to this system. Three of them you build. One is the model.

Your Identity File

Start with one file. A plain text document that describes how you think. Copy it into your AI tool's custom instructions. The model reads it before every conversation.

Template

# [Your Name] — AI Identity File

## Who I am
[Role, domain, what you already know — so the model doesn't over-explain]

## How I think
[How you process information. Systematic? Visual? Intuition-first?]

## What I value
[Actual values in your work. Directness? Precision? Speed? Craft?]

## How I make decisions
[Under uncertainty: options first? One recommendation? Think out loud?]

## Tone and style
[What kind of responses work for you. Length, format, what annoys you.]

## Current focus
[Live projects, active decisions. Update this regularly.]

## Hard constraints
[What the model should never do without asking you first.]

Part 1: The philosophical layer

  1. How do you think and process information?
  2. What do you actually value in your work?
  3. How do you make decisions when things are unclear?
  4. What should AI never do on your behalf?

Part 2: The operational layer

  1. Your professional context: role, domain, what you already know
  2. Tone and response style: direct or discursive? Options or one recommendation? How long?
  3. What annoys you in responses
  4. Current focus areas (update this regularly)

Example

How I think: Systematically. I prefer frameworks and patterns over gut feel.

What I value: Speed with precision. Being wrong fast beats being right slowly.

How I decide: Options first, then a recommendation. Walk me through the reasoning.

Tone: Direct. Short sentences. Tell me what's weak, not just what's good.

What annoys me: Hedge language like "it might be." Either say it or don't.

Current focus: Shipping products. Data quality. Teams.

Where to Put It

ChatGPT: Settings → Personalization → Custom Instructions → paste your file

Claude.ai: Create a Project → Add project instructions → paste your file

Session Prompts

Different sessions need different opening frames. Pick the right one.

Planning (figuring something out)

I'm trying to figure out: [X]. My goal is: [Y]. I don't want solutions yet — walk me through the problem first. Ask me clarifying questions. Then help me think through the options.

Execution (you know what you want)

I need to get [X] done today. Here's exactly what I want: [specific output]. My constraints: [time / format / audience]. Draft it. Then I'll tell you what to adjust.

Review (checking what you have)

Here's what I produced: [paste]. I want you to check it against [goal / criteria]. Be direct. Tell me what's weak, not just what's good. If something is missing, name it specifically.

Small Things Add Up

Customizing AI isn't one big setup. It's small deliberate choices that compound. Configure a notification when Claude stops so you're not watching a screen. Set a keyboard shortcut you actually use. Write down one decision rule. Start tonight with the identity file. Everything else follows.

For Developers

Making Claude Code Yours

You already have Claude Code running. This track is about the system you build around it: files, rituals, and patterns that turn a generic model into something that works with how you think.

Layer 1: CLAUDE.md

A plain text file at your project root. Claude reads it before every conversation. For global defaults, put it in ~/.claude/CLAUDE.md.

Template

# CLAUDE.md — 12-rule template

These rules apply to every task in this project unless explicitly overridden.
Bias: caution over speed on non-trivial work. Use judgment on trivial tasks.

## Rule 1 — Think Before Coding
State assumptions explicitly. If uncertain, ask rather than guess.
Present multiple interpretations when ambiguity exists.
Push back when a simpler approach exists.
Stop when confused. Name what's unclear.

## Rule 2 — Simplicity First
Minimum code that solves the problem. Nothing speculative.
No features beyond what was asked. No abstractions for single-use code.
Test: would a senior engineer say this is overcomplicated? If yes, simplify.

## Rule 3 — Surgical Changes
Touch only what you must. Clean up only your own mess.
Don't "improve" adjacent code, comments, or formatting.
Don't refactor what isn't broken. Match existing style.

## Rule 4 — Goal-Driven Execution
Define success criteria. Loop until verified.
Don't follow steps. Define success and iterate.
Strong success criteria let you loop independently.

## Rule 5 — Use the model only for judgment calls
Use me for: classification, drafting, summarization, extraction.
Do NOT use me for: routing, retries, deterministic transforms.
If code can answer, code answers.

## Rule 6 — Token budgets are not advisory
Per-task: 4,000 tokens. Per-session: 30,000 tokens.
If approaching budget, summarize and start fresh.
Surface the breach. Do not silently overrun.

## Rule 7 — Surface conflicts, don't average them
If two patterns contradict, pick one (more recent / more tested).
Explain why. Flag the other for cleanup.
Don't blend conflicting patterns.

## Rule 8 — Read before you write
Before adding code, read exports, immediate callers, shared utilities.
"Looks orthogonal" is dangerous. If unsure why code is structured a way, ask.

## Rule 9 — Tests verify intent, not just behavior
Tests must encode WHY behavior matters, not just WHAT it does.
A test that can't fail when business logic changes is wrong.

## Rule 10 — Checkpoint after every significant step
Summarize what was done, what's verified, what's left.
Don't continue from a state you can't describe back.
If you lose track, stop and restate.

## Rule 11 — Match the codebase's conventions, even if you disagree
Conformance > taste inside the codebase.
If you genuinely think a convention is harmful, surface it. Don't fork silently.

## Rule 12 — Fail loud
"Completed" is wrong if anything was skipped silently.
"Tests pass" is wrong if any were skipped.
Default to surfacing uncertainty, not hiding it.

Layer 2: Memory System

Flat files in ~/.claude/projects/<project>/memory/. Four types:

  • user_*.md — who you are, how you work
  • feedback_*.md — corrections and confirmed approaches
  • project_*.md — live decisions, what's in progress
  • reference_*.md — where to find external information

Each file has frontmatter: name, description, type. An index file MEMORY.md stays one line per memory and is always loaded. Claude reads all of it at the start of every conversation.

Layer 3: Session Rituals

Different session types need different opening frames.

Planning (figuring something out, not executing yet)

/session-start [planning] Working on: [X] Goal for this session: figure out [Y], not execute it. Call tools as needed to help me think. Walk me through things if I'm unclear. Mix options if there's more than one good path. Don't move to execution until I say so.

Execution (you know what you want, go fast)

/session-start [execution] Working on: [X] I know what I want. Execute [specific task]. Check in at natural breakpoints. Don't ask for permission on small decisions.

Review (critical feedback on existing work)

/session-start [review] Working on: [X] Here's what was produced: [link/paste]. I want a critical review against [criteria]. Be direct about what's weak.

Layer 4: Plan Mode as a Working Pattern

The most underused feature for non-engineers. The workflow:

  1. Enter plan mode before any execution
  2. Think out loud: ask Claude to walk you through the problem, call tools mid-plan for real data, mix options, ask "why" questions
  3. When the plan is clear, exit plan mode and execute
  4. The discipline: never execute until the plan is actually clear. Plan mode is the thinking space.

This shifts Claude from autocomplete to thinking partner with selective execution. The execution happens faster because the thinking happened first.

Small Things Add Up: Hooks and Notifications

Add a macOS notification when Claude stops or needs input. Two minutes of setup, changes how the session feels.

In ~/.claude/settings.json: { "hooks": { "Stop": [ { "matcher": "", "hooks": [ { "type": "command", "command": "osascript -e 'display notification \"Claude is done\" with title \"Claude Code\"'" } ] } ] } }

The point isn't the notification. The point is that every small deliberate customization compounds. That's what building a system around the intelligence looks like.
